## Цель для обучающегося

После просмотра обучающийся должен уметь объяснить механизм четырёх атак 2-го уровня: (1) VLAN hopping через поддельный DTP/802.1Q — почему виноват режим `dynamic auto`/`dynamic desirable`; (2) double-tagging — как внешний тег native VLAN «снимается» первым коммутатором, а внутренний тег доставляет кадр в чужую VLAN; (3) DHCP starvation — исчерпание пула через поддельные MAC; (4) DHCP spoofing — подставной сервер выигрывает «гонку» DORA и раздаёт ложный шлюз/DNS/IP. И знать первые контрмеры: `switchport mode access` на портах доступа, запрет авто-транкинга, native VLAN только на транках.

Текст темы (10.5.2–10.5.5) описывает все четыре атаки подробно, с пошаговыми иллюстрациями (double-tagging — 3 шага, DHCP spoofing — 5 шагов). Видео дублирует текст почти полностью; из нового — два конкретных фрагмента CLI в выносках (`switchport mode dynamic auto | dynamic desirable` как причина уязвимости, `switchport mode access` как мера), анимация «снятия» внешнего тега при проходе кадра по транку, краткий повтор DORA (DHCPDISCOVER broadcast → DHCPOFFER unicast → DHCPREQUEST broadcast → DHCPACK unicast) с примером выданных параметров и кадр из Windows-утилиты смены MAC-адреса как иллюстрация к starvation.

## Предложение по пересборке

**Формат:** `текст + иллюстрация` для VLAN hopping, starvation и DORA (текст 10.5.2/10.5.4/10.5.5 уже покрывает их полностью) **плюс** две короткие анимации Figma (≤ 60 с каждая) там, где важна динамика: (а) «double-tagging: кадр теряет внешний тег» и (б) «DHCP spoofing: гонка двух Offer». Озвученный ремейк всего ролика не нужен — он был бы пересказом текста темы. Суммарно ≈ 1:30 анимации.

Сцены для генератора:

*Анимация A — двойное тегирование (≤ 60 с):*
1. Схема: SW1 — транк (Native VLAN = 10) — SW2; атакующий на порту доступа VLAN 10 у SW1; Target (VLAN 20) у SW2. Над атакующим кадр `Ethernet | VLAN 10 | VLAN 20 | Data` → подпись «Атакующий в VLAN 10 строит кадр с двумя тегами».
2. Кадр входит в SW1; поле `VLAN 10` подсвечивается и исчезает → «SW1 снимает внешний тег: VLAN 10 — native, по транку идёт без тега».
3. Кадр `Ethernet | VLAN 20 | Data` движется по транку в SW2 → «SW2 видит только тег VLAN 20».
4. Поле `VLAN 20` исчезает, кадр `Ethernet | Data` спускается к Target → «Кадр доставлен в VLAN 20 — без маршрутизатора».
5. На три порта доступа «прилипает» ярлык `switchport mode access`, транк — `switchport nonegotiate`, native VLAN меняется на 999 → «Защита: порты доступа — только access, транки — вручную, native VLAN — отдельная и неиспользуемая».

*Анимация B — подмена DHCP (≤ 60 с):*
1. Клиент, легитимный DHCP-сервер и Rogue DHCP (ноутбук злоумышленника) на одном коммутаторе → «Клиент включается».
2. Broadcast `DHCPDISCOVER` расходится во все стороны → «Discover видят оба сервера».
3. Два `DHCPOFFER` летят к клиенту; подставной приходит первым (ближе) → «Клиент примет первое предложение».
4. Broadcast `DHCPREQUEST`, затем `DHCPACK` от подставного сервера с полем «Default Gateway: 192.168.10.99 (атакующий)» → «Шлюз — машина злоумышленника: весь трафик идёт через него».
5. Ярлык `ip dhcp snooping` на коммутаторе, порт сервера «trusted», остальные «untrusted», Offer от подставного — отброшен → «Ответ: DHCP snooping (тема 11)».

Ассеты: пара коммутаторов с транком и подписью native VLAN; фигура злоумышленника; полоса кадра с отделяемыми тегами (VLAN 10 жёлтый, VLAN 20 розовый); конверты DHCP-сообщений с подписями DISCOVER/OFFER/REQUEST/ACK и признаком broadcast/unicast; ярлыки с командами CLI.

CLI-фрагменты, которые нужно показать (из выносок видео, для 11.x симулятора они же — упражнение «закрыть порты»):

```
Switch(config-if)# switchport mode dynamic auto
Switch(config-if)# switchport mode dynamic desirable   ! уязвимые режимы по умолчанию
Switch(config-if)# switchport mode access              ! мера защиты на портах доступа
```

## Транскрипт

```
[0:04] A VLAN hopping attack is going to enable traffic from one virtual local area network to be seen by another virtual local area network, and this is without the aid of a device such as a router. This is a basic VLAN hopping attack: a threat actor is going to configure a host to act just like a switch and then, using that host, they're going
[0:25] to take advantage of the automatic trunking port feature that's enabled by default on most switch ports. This would be the modes of dynamic auto or dynamic desirable on the switch ports. The threat actor is going to configure the host to spoof those 802.1Q signaling and those DTP messages so that the trunk will form between the host and the
[0:46] switch. With a successful trunk established they're going to be able to send and receive traffic on any virtual local area network, effectively hopping between any VLANs that they want to connect through. With a VLAN double tagging attack a threat actor is going to embed a hidden 802.1Q VLAN tag inside of a frame that
[1:08] already has an 802.1Q VLAN tag. What's going to happen here is we're going to have an attacker that's going to double tag a frame. For example, our attacker was going to build a message that's going to communicate from its current VLAN, which is VLAN 10, with a targeted VLAN of VLAN 20. With the attacker currently being on
[1:30] VLAN 10 they're going to build a frame that's going to have an external VLAN header on it, a VLAN 10, and then an internal tagged VLAN of VLAN 20. When that message is sent up to the first switch, our first switch is going to see the external outside header of VLAN 10, it's going to strip that off and then send this traffic on its way to any
[1:50] device running in VLAN 10. Well, the switch sees that VLAN 10 is also the native VLAN, so it's going to remove the VLAN 10 header and move it across the trunk link. Now as that frame moves across the trunk link the first header of VLAN 10 was removed and now the internal tag, which is the VLAN 20, that still exists. This second switch is going to receive
[2:12] that frame, it's going to strip off that VLAN 20 header and then it's going to forward it out any VLAN 20 ports, which includes down to that targeted host. This is effectively allowing our threat actor machine on VLAN 10 to communicate to the target on VLAN 20 using a double tag. Now VLAN hopping and this whole idea of VLAN double tagging, they can both be
[2:33] prevented by putting in a couple security guidelines. Number one, we should get rid of trunking on any access port that goes to end devices. Also the whole idea of auto trunking using things like dynamic desirable and dynamic auto — that should be disabled; we should use a manual static trunking as needed. Also native VLANs should only be used on trunk links, and that native VLAN should
[2:55] never span to a user device. For instance, in this scenario — this scenario only works when the threat actor is on the same VLAN as the native VLAN between our switches. DHCP is a powerful tool for easy dynamic addressing across our networks, but it
[3:15] can also be a powerful tool for malicious threat actors that want to have some fun with the network. So, quick recap of DHCP: we have DHCP servers that are going to dynamically provide addressing for us. That addressing includes IP addresses, subnet mask, default gateway, DNS servers and even more with DHCP options to our clients.
[3:36] The typical conversation with DHCP goes back to DORA: Discover, Offer, Request, Acknowledge. Our client is going to send a broadcast message which is a Discover; a server is going to hear that broadcast message and respond with a unicast Offer of "this is what I can give you, here's some addressing info". The client receives that offer, it's very
[3:56] excited and it sends out a broadcast of "I accept the offer you sent me". That server finishes it up with a unicast saying "you like the offer, I'm glad, I acknowledge", and then the lease is complete regarding the client taking that addressing info. It sounds easy enough, but now let's bring in an attack.
[4:16] Now it sounds funny saying it, but there's two common types of DHCP attacks: we've got the DHCP starvation attack and DHCP spoofing. With DHCP starvation the goal of the threat actor is to create a denial of service for your connecting clients. What would happen is the threat actor would gobble up all of the usable
[4:37] DHCP-provided addresses. The easiest way to go about this is having a threat actor using a client machine that's cycling through source MAC addresses very quickly and for each source MAC address gobbling up an available IP address being given by your DHCP server. When all the addresses are taken from the DHCP server there's nothing to
[4:57] provide the legitimate clients. On top of that there's the DHCP spoofing attack. Imagine having a threat actor putting out their own DHCP server on your network, and when your clients use the whole DORA process and they broadcast out for a Discover, and then there's the Offer, the Request — but then your rogue DHCP server finishes the
[5:18] conversation with a client with an acknowledgement providing wrong default gateway info, incorrect DNS servers, as well as even wrong IP addresses for the clients to use. Effectively your legitimate clients cannot communicate on the network. So we have to prevent this by using safeguards and implementations for security.
```
